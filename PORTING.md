# Porting inventory

`rea-rs` ports [REA](https://github.com/morluto/rea) capability by capability. This file is the map: what upstream contains, where each part lands in the Cargo workspace, what is ported, and in what order the rest should follow. Rules for porting are in [AGENTS.md](AGENTS.md); maintainer decisions are in [LEARNING.md](LEARNING.md); the crate composition is in [docs/architecture.mermaid](docs/architecture.mermaid).

Sizes are non-test / test TypeScript lines under `upstream:src` at the mirrored commit (`git rev-parse refs/heads/upstream`). Upstream also has about 21 MB of fixtures and acceptance tests under `upstream:tests/`. The whole port is a multi-session effort; do not read the table as a schedule.

## Status

| Status      | Meaning                                                                        |
| ----------- | ------------------------------------------------------------------------------ |
| **ported**  | Rust implementation, ported tests, public CLI test. MCP exposure still pending. |
| **partial** | Part of the area exists; the gap is named.                                     |
| **pending** | Nothing yet.                                                                   |

MCP is pending everywhere: no tool is exposed over MCP until the server adapter lands (wave 1).

## Intentional divergences

- **Default CLI output** is JSON. Upstream defaults to `toon`; that and `yaml`, `md`, `csv`, `tsv`, `jsonl`, `--filter-output`, `--columns`, `--token-limit`, `--full-output`, and `--timings` belong to the CLI envelope (wave 1) and are rejected or absent until then.
- **Descriptor cleanup.** Upstream models read-only descriptor close failure as a retained cleanup obligation (`ArtifactResourceScope`). `rea-filesystem` closes on `Drop`; a read-only descriptor holds no buffered writes, so a close failure has no caller-visible consequence. Revisit when a writing resource (extraction, output trees) is ported.
- **Concurrency model.** Providers are synchronous and cancel through `CancellationSignal` polling; async callers run them as blocking work. Upstream threads an `AbortSignal` through promises.

## Wave order

1. **Foundations.** `rea-process`, `rea-config`, CLI output envelope, MCP stdio server, the typed `analysis_profile` and `relationship_coverage`, and the deferred error tags. Every later wave depends on these.
2. **In-process readers.** Cheapest per capability and fully testable without third-party tools; each carries one CLI command and one MCP tool.
3. **External-tool providers.** One at a time, each behind the process module with the lifecycle regressions from `upstream:docs/testing.md`. Real-provider verification is separate from simulated coverage and must be reported separately.
4. **Browser, JavaScript, setup, sessions.** Needs the open questions below answered before substantial implementation (AGENTS.md: fail-closed integration).

## Scope decisions

Recorded in [LEARNING.md](LEARNING.md). Summary of what each one changes here:

| Item                          | Decision                                                | Consequence                                                                                   |
| ----------------------------- | ------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Node.js                       | Gone entirely, including optional bindings.             | Every Node-backed upstream component is reimplemented in Rust.                                |
| JavaScript source-map codec   | Port to Rust.                                           | Replaces the owned Node codec child. Port `SourceMapFormat`, `TraceSourceMap`, and their tests with the existing limits. No Rust source-map crate is in the offline cache, so the decoder is written in-repo or a crate is justified when added. |
| Frida                         | Port to Rust; FFI only if very limited.                 | One small FFI crate owns every `unsafe` block; other crates stay `unsafe_code = deny`.        |
| Target execution / injection / mutation | Run in containers (podman).                   | A container runner owns the target's lifecycle (likely beside `rea-process`). Podman is bring-your-own. |
| Tests                         | `cargo test`.                                           | vitest, fast-check, and Stryker are not ported.                                               |
| Playwright                    | **Open.**                                               | See below.                                                                                    |

### Open: Playwright replacement

Upstream's browser scenario and Electron capture drive pages through `playwright-core` (`PlaywrightScenario*`, `PlaywrightElectron*`, `ElectronCaptureCleanup`). It is not a test dependency. The code only references Chromium and Electron (inferred from identifier counts). Playwright for Chromium is a CDP driver, and upstream already has a CDP provider (`CdpBrowserProvider`, `ws`). Proposed: replace it with a Rust CDP client over WebSocket for Chromium and Electron, and drop Firefox/WebKit unless the maintainer wants them. Needs confirmation.

### Open: container policy

Before any target-execution capability (`debug-with-*`, Frida, `capture-process`, browser and Electron launch) is ported, decide:

1. **Image.** Caller-supplied, or a Containerfile kept in the repo?
2. **Network.** Default none, with an explicit opt-in?
3. **Mounts.** Target read-only, plus a separate writable output mount?
4. **Privileges.** Rootless only; which capabilities (for example `SYS_PTRACE` for debuggers and Frida) and whether a custom seccomp profile is needed.
5. **Platform limits.** Windows and macOS targets cannot run in a Linux container. Fail closed, or a different route?
6. **Ownership.** How container identity and cleanup retry fit the `rea-process` model (a container name alone does not prove ownership after exit or reuse).

## Checklist for porting one capability

1. Read the upstream contract first: `upstream:src/domain/<area>`, `src/application/<area>`, the CLI command, the MCP registration, and `upstream:tests/acceptance/<area>*`. Run `git log refs/heads/upstream -- PATH` for fixes since the last port.
2. Domain: result declarations in field order, input parsing with the upstream issue projection, provider identity.
3. Provider: the reader or process adapter, mapping every failure exactly as upstream does.
4. Application: the service (input admission, report validation, Evidence creation).
5. Adapters: CLI command, MCP tool. Preserve names, flags, schemas, error contracts, and Evidence shapes.
6. Tests: port unit and acceptance cases; prefer the public CLI/MCP path. State which parity was verified and which was not.
7. `cargo xtask ci`, update this file, commit with a Conventional Commit subject.

## Parity record

Verified by running upstream code: canonical digest vectors only.

Not run (upstream `node_modules` are unavailable here, so the full upstream CLI cannot execute): Evidence identifiers, error projections, ELF note results, and CLI output are checked against upstream source and ported tests, not against upstream output. Comparing Rust output with upstream output on shared fixtures is the next parity step once an upstream build is available.
